# Theming

The site ships four complete looks. Anyone can switch between them from the
picker in the site header, and the choice follows them across every page —
blog posts, hub pages, the calendar, the Hub Finder.

This exists so you can put real options in front of people and let them react
to a working site rather than a mockup, without touching a word of content.

---

## 1. Showing the options to volunteers

**In the header.** Every page has a theme dropdown next to the dark-mode
toggle. Pick a look; it applies immediately and is remembered in that
browser, so clicking through to the blog or the map keeps it.

**By link.** Send someone straight into one look:

| Link | What they see |
| --- | --- |
| `?theme=beacon` | Beacon, light |
| `?theme=sound&mode=dark` | Sound, dark |
| `?theme=rainier` | Rainier, light |
| `?theme=` | Back to the default |

So `https://<site>/index.html?theme=sound&mode=dark` opens in that theme, and
it sticks as they browse. Good for an email to a group: four links, four
looks, same site.

The dark/light toggle is independent of the theme — each of the four has its
own dark mode, so there are eight combinations in total.

### The four themes

| Theme | Character |
| --- | --- |
| **Default — Harbor Blue** | The current site. Unchanged. |
| **Rainier — Evergreen** | Civic and settled. Evergreen and stone, a serif voice, square corners, almost no shadow. |
| **Sound — Teal** | Open and modern. Teal on near-white, large soft corners, roomy header, geometric sans. |
| **Beacon — High Visibility** | Reads like emergency signage. Navy and safety amber, heavy rules, square, the most legible of the four. |

They differ in typography, corner radius, shadow depth and header density as
well as colour — a palette swap alone doesn't read as a different site.

### When the demo is over

Open [`js/theme.js`](../js/theme.js) and set:

```js
var SHOW_PICKER = false;
```

The picker disappears; saved choices and `?theme=` links keep working. To
remove theming altogether, drop the `themes.css` link and the `theme.js`
script from the pages. To make one of the looks permanent instead, move its
token values into the `:root` and `[data-theme="dark"]` blocks of
`css/style.css`.

## 2. Adding a new theme

Three steps, no page edits:

**1.** Copy both blocks from
[`css/themes/_template.css`](../css/themes/_template.css) into
[`css/themes.css`](../css/themes.css) and replace `myskin` with your id.

**2.** Add it to the picker in [`js/theme.js`](../js/theme.js):

```js
{ id: 'myskin', label: 'My Skin - Warm and calm', note: 'Shown in the tooltip' }
```

**3.** Check it:

```bash
npm run check
```

Every page already loads `css/themes.css`, so the new look reaches the whole
site at once — including blog posts, which are generated by
`tools/build-blog.mjs` from the same template.

Delete any token you're happy with. Anything a skin omits falls back to
`css/style.css`, so a ten-line skin that changes three colours is a perfectly
good skin.

### The selector pattern

Copy it exactly:

```css
[data-skin="myskin"]:not([data-theme="dark"]) { /* light */ }
[data-skin="myskin"][data-theme="dark"]       { /* dark  */ }
```

Both are specificity `(0,2,0)`, so they outrank the `(0,1,0)` `:root` and
`[data-theme="dark"]` blocks in `style.css`, and they're mutually exclusive so
light values can't leak into dark mode.

A bare `[data-skin="myskin"]` is only `(0,1,0)` — the same as `style.css`'s
dark block — and being in a later file it would **beat** it, so your light
colours would win in dark mode. That's the one real trap here.

### How the switching works

Two independent attributes on `<html>`:

| Attribute | Meaning | Set by |
| --- | --- | --- |
| `data-skin` | the palette; absent = default | the picker, via `js/theme.js` |
| `data-theme` | `dark`, or absent for light | the toggle, via `js/main.js` |

Both persist in `localStorage` (`seh-skin`, `seh-theme`). A small inline
script in each page's `<head>` applies them **before first paint**, so there's
no flash of the wrong theme. That script is also what reads `?theme=` and
`?mode=` — which is why it has to stay inline and in the head rather than move
into `theme.js`.

`js/theme.js` exposes `window.SEHTheme` (`get`, `set`, `isDark`, `token`,
`mapStyles`, `onChange`) for anything that needs to react in JS.

## 3. The one rule

> A colour, gradient or shadow literal must not appear below the theme layer.

Everything that decides how the site looks lives in the theme layer at the top
of [`css/style.css`](../css/style.css); the rest of the stylesheet only reads
those tokens through `var()`. A literal down in the rules is a value no theme
can reach — it looks fine until someone writes a second theme, and then it's a
bug that shows up in only one of them.

`npm run check:theme` walks the repo for every `.css` file and every page with
an inline `<style>` block, and fails if it finds a hex, `rgb()`, `rgba()`,
`hsl()` or `hsla()` outside a token block. A page you add later is covered
automatically.

> **Note:** none of these checks are part of the Netlify build, which runs
> only `npm run build:blog`. Nothing runs them for you — run `npm run check`
> before you commit.

So instead of this:

```css
.pledge-card { background: #eaf4fb; }
[data-theme="dark"] .pledge-card { background: #1e3a5f; }
```

add a token and reference it:

```css
/* in the theme layer of css/style.css */
:root              { --surface-pledge: #eaf4fb; }
[data-theme="dark"]{ --surface-pledge: #1e3a5f; }

/* down in the rules */
.pledge-card { background: var(--surface-pledge); }
```

The second form is shorter, and all four themes can restyle it for free.

### Keep the dark block to token overrides

An element rule inside `[data-theme="dark"]` — `[data-theme="dark"] .notice
{ background: … }` — is the same mistake in disguise: the colour is still
outside the theme layer, so a skin can't reach it. Express the difference as a
token that dark redefines.

### Deliberate exceptions

Some things must not follow the theme: the brand's Dark Slate logo backdrop,
and the photo lightbox, which stays dark in both modes so images read
consistently. Mark those with a comment containing `theme-exempt` directly
above the rule:

```css
.logo-card-preview.dark-bg {
  /* theme-exempt: brand Dark Slate, the documented backdrop for the
     reversed logo. Must not follow the site theme. */
  background: #1a2e3a;
}
```

Exemption is **per rule, not per declaration** — a component that stands
outside the theme does so as a whole, and marking one of its five colours
would be a trap for whoever edits the other four. Say *why*; "theme-exempt"
alone tells the next reader nothing.

## 4. Choosing values that stay readable

`npm run check:contrast` resolves all four themes the way a browser would, in
light and dark, and measures the WCAG contrast of the pairs that actually meet
on screen — body text on its background, button ink on each brand colour,
footer, notices, badges. It fails on anything below AA (4.5:1 for body text,
3:1 for headings).

Run it on every new skin. It catches the mistakes that are invisible until
someone can't read the site:

- **`--color-on-brand`** is the ink on filled brand colours (buttons, hero,
  tags, date blocks). A skin with a *light* primary must darken it. Keep
  primary, secondary and accent similar in lightness so one ink serves all
  three.
- **`--color-on-alert`** is separate because the alert red stays dark in every
  theme — so it usually stays light even in a skin where `--color-on-brand`
  went dark.
- **Overlays must stay translucent.** `--overlay-*` tints sit over whatever is
  beneath them: light themes darken, dark themes lighten. An opaque value
  flattens the header controls and dropdowns.
- **Semantic text vs. tinted panel.** `--color-success` / `--color-danger` are
  text-weight colours; `--surface-success` / `--surface-danger` are the panels
  behind them. Dark mode lightens the *text* tokens because the brand green
  and red are unreadable on a dark ground — change each pair together.
- **`--surface-preview` / `--surface-media`** are deliberately neutral
  backdrops for logos and photos. Artwork shouldn't pick up a brand tint.
- **`--shadow`** needs more opacity on a dark ground to be visible at all.

### Known exceptions

The check reports six pairs it does not fail on, all in the **default**
palette and all pre-dating any theming work: white on Medium Blue `#2e86c1`
(3.97:1), white on Signal Orange `#ff4d00` (3.33:1), and two marginal ones in
the footer and success notice. Those are brand colours from
[`branding.html`](../branding.html) — changing them is a brand decision, not a
code one, so they're listed in `PREEXISTING` in the checker with a note.
Delete an entry the day the brand colour changes. The three new themes meet AA
on every pair.

## 5. What the theme does *not* reach

Honest limits, so nobody hunts for a bug that isn't there:

- **The Neighborlink map** on `map.html` is a Google *My Maps* iframe. Google
  draws it and offers no styling parameters, so it stays the same in every
  theme. Only its frame follows.
- **The calendar** embeds accept exactly one colour, `bgcolor`, which
  `js/theme.js` sets from `--embed-calendar-bg`. Google's embed has **no dark
  mode**, so that token deliberately stays light in both themes — a dark value
  leaves Google's own dark text unreadable. Changing it reloads the iframe.
- **The Hub Finder map** *does* follow the theme: it uses the Maps JS API, so
  `js/theme.js` builds a style array from the tokens and the markers read
  their colours from the palette. This one needs an API key to see locally.
- **The line-of-sight profile** in the Hub Finder keeps fixed red/amber/green,
  because those are legend-coded status colours rather than decoration.

## 6. Verifying a change

```bash
npm run check          # all three below
npm run check:theme    # no colour literals outside the theme layer
npm run check:contrast # all themes readable, light and dark
npm run test:theme     # the picker, saved choice and ?theme= links still work
```

`test:theme` runs `js/theme.js` and the real inline `<head>` script against a
stubbed DOM. There's no browser in this project, so that test is what stands
between a working picker and one that silently does nothing.

There's also `tools/verify-theme-parity.mjs`, which proves a *refactor*
changed nothing on screen. It resolves `var()` chains to literals, expands
border shorthands to longhands, and builds a `(media query, selector,
property) -> computed value` map per theme, then diffs two stylesheets.
Moving a colour into a token leaves the maps identical, so any difference is a
real visual change:

```bash
git show HEAD:css/style.css > /tmp/before.css
node tools/verify-theme-parity.mjs /tmp/before.css css/style.css
```

Use it when tokenising existing CSS, where "nothing changed" is the whole
claim. It's not for intentional redesigns, where you *want* the maps to
differ. Note it compares declared values, not rendered pixels, and ignores
source order between different selectors — so check those separately if you
move rules around.

---

## 7. Adding a new component

1. Write the rules using existing tokens. Most components need nothing new.
2. If you reach for a colour no token expresses, add the token to the theme
   layer — in **both** `:root` and `[data-theme="dark"]` if the modes differ —
   then reference it.
3. `npm run check`.
4. If you added a token, add it to `css/themes/_template.css` too, so skin
   authors can see it. That file is meant to list the complete surface.
